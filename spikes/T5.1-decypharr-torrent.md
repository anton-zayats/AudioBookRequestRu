# T5.1 — Decypharr as the torrent download client

Investigation into routing **torrent** audiobook results through **Decypharr**
(`sirrobot01/decypharr`) — either directly from ABR (Path A) or as Prowlarr's
download client (Path B). Research-only; no application code, tests, or config
were changed. Builds on `spikes/T0.1-decypharr-download-client.md` and `plan.md` §6.1.

---

## 1. Executive recommendation

- **Path A (direct `DecypharrClient`) is the right target**, and **Path B is a
  viable zero-code interim**. The plan's doubt ("a Prowlarr-side client may not be
  used by ABR's grabs") is **resolved: it *is* used** — see §3.
- **Magnet-first, `.torrent` as fallback.** Decypharr converts both to the same
  thing internally (it parses `.torrent` → infohash → submits a magnet to debrid),
  so a magnet URI avoids having ABR re-fetch the tracker's `.torrent`. Use
  `TorrentSource.magnet_url` when present; otherwise fetch `TorrentSource.download_url`
  and POST the `.torrent` file.
- If the owner only needs *torrents to reach debrid* and is happy with the same
  "2xx = done" semantics as today, **Path B works with only Prowlarr/Decypharr
  config changes** — no ABR code. If ABR must *guarantee bytes land in the
  Audiobookshelf-watched folder* and *know when they're done*, only Path A gives
  that control (via an explicit `download` action and the state API).

---

## 2. How this differs from aria2 (read `app/internal/downloads/client.py`)

The existing ABC is a direct-HTTP shape:

```python
class DownloadFile(BaseModel):
    urls: list[str]
    out: str | None = None

class DownloadClient(ABC):
    async def test_connection(self) -> bool: ...
    async def enqueue(self, files, *, dir, headers=None) -> list[str]:
        """one identifier (GID) per file"""
    async def status(self, gid) -> dict | None: ...
```

A torrent/Decypharr client **cannot honor three of those semantics**, and must be
allowed to reinterpret them (see §5):

| ABC knob | aria2 | Decypharr (qBittorrent-compatible path) |
|---|---|---|
| `DownloadFile.urls` | list of HTTP source URLs | **one magnet URI**, or **one `.torrent` URL to fetch** |
| `DownloadFile.out` | `out` (final filename) | **ignored** (release name kept; no per-file rename) |
| `enqueue(..., dir=...)` | per-request `dir` | **ignored** — Decypharr ignores qBittorrent's `savepath`; files always land in `<download_folder>/<category>` |
| return value (`gid`) | aria2 GID | **infohash** (must be computed client-side; `/torrents/add` returns `200` with an empty body) |
| `headers` | sent to the HTTP source | only useful when fetching the `.torrent` before add, never sent to Decypharr |

Consequence: `DecypharrClient.enqueue(files, dir=...)` should *accept but ignore*
`dir`/`out` and raise/log if the caller expects per-book directories (the target
folder is Decypharr-side). Routing by protocol remains: `torrent` → Decypharr (or
Prowlarr), `direct` → aria2.

## 3. Path B — is Prowlarr-side Decypharr actually used by ABR's grab?

**Yes — viable.** This is the one place where `plan.md` §6.1's tentative doubt is
wrong, and it is worth being precise about why.

Prowlarr documents its "Download Clients (Prowlarr Searches)" as:

> "If you intend to do searches directly within Prowlarr, you need to add Download
> Clients. Otherwise, you do not need to add them here. For searches from your Apps,
> the download clients configured there are used instead."
> "Download clients are for Prowlarr in-app searches only and do not sync to apps."

ABR's torrent flow is **two Prowlarr calls** that map onto Prowlarr's *own*,
in-app search machinery, not onto a synced *Arr app:

1. `GET /api/v1/search?query=…` — the Prowlarr "Search Feed" (returns
   `guid`/`indexerId`/`downloadUrl`/`magnetUrl`). This is the query step.
2. `POST /api/v1/search` with `{guid, indexerId}` — **Prowlarr's manual-grab
   endpoint**, the same action as the UI's "download icon" / "Grab Releases"
   button. The Servarr Search wiki states, of that button, it "will send it to the
   proper download client you have configured."

Because step 2 *is* an in-app Prowlarr grab (ABR merely triggers it via API),
Prowlarr dispatches it to **its own configured "Download Clients (Prowlarr
Searches)"** — i.e. the qBittorrent entry pointing at Decypharr. "App searches"
in the Servarr note means Sonarr/Radarr/Lidarr/Readarr doing their *own* grab via
synced Torznab/Newznab feeds and their *own* download clients — which is not what
ABR does (ABR has no indexer sync and no own-grab; it delegates the grab to
Prowlarr). `golift.io/starr/prowlarr.Grab(guid, indexerID)` is just this endpoint.

So a Decypharr entry in Prowlarr → Settings → Download Clients *is* reached by
ABR's `start_download()`. The catches are entirely Decypharr-side config (§6):

- the Prowlarr qBittorrent client's **Category** field must be non-empty and equal
  to a Decypharr Arr name (`arr is required` → `502 provider_error` otherwise);
- credentials must satisfy Decypharr's `use_auth` (username/password, API token
  in the password, or a *saved* Arr's host+API-key as username/password);
- a debrid provider must be configured;
- the materialization action must be `download` (or a working `symlink` mount).

**Path B limitations vs Path A:** Prowlarr drives the qBittorrent mock, so ABR
cannot force `sequentialDownload=true` (Decypharr's "force download-action" hint),
cannot set `downloadUncached`, and gets no Decypharr state back — Prowlarr is
fire-and-forget and ABR already marks `book.downloaded = True` on a 2xx. If the
global `default_download_action` is the default `symlink` and no mount is working,
bytes never reach disk; ABR won't know.

## 4. Path A — exact HTTP calls

Decypharr exposes `POST /api/v2/auth/login`, `POST /api/v2/torrents/add`,
`GET /api/v2/torrents/info`, `GET /api/v2/app/version`, etc. at
`http://<host>:8282` (default port; configurable). It advertises qBittorrent
`v4.3.2` / WebAPI `2.7` so it looks like a normal qBittorrent to Prowlarr.

### 4.1 Auth

Two supported styles (from `pkg/server/qbit/context.go` + docs):

**(a) Cookie (qBittorrent-style).** Login → reuse the `SID` cookie.

```http
POST /api/v2/auth/login HTTP/1.1
Host: decypharr:8282
Referer: http://decypharr:8282          # qBittorrent WebUI requires exact-origin Referer/Origin
Content-Type: application/x-www-form-urlencoded

username=dcyadmin&password=<decypharr-password>
```

```http
HTTP/1.1 200 OK
Set-Cookie: SID=<base64(username|password|hash)>; Path=/
Content-Length: 3

Ok.
```

Failure → `401` (Decypharr does not return qBittorrent's `Fails.` body).

**(b) Bearer API token (recommended for an ABR client).** Skip login entirely.
Send `Authorization: Bearer <api_token>` on every request (token from Decypharr
Settings → Auth). Decypharr's `getUsernameAndPassword` checks the `Authorization`
header *before* the cookie, and `config.VerifyToken(password)` accepts the token.

Note: the API token and an Arr's API key are **different credentials**. There is
also a third mode (per-Arr): username = Arr host, password = Arr API key, and the
Arr must already be **saved** in Decypharr (Settings → Arrs) for `MatchCredentials`
to succeed — "Decypharr checks saved Arr credentials without contacting the Arr
server."

### 4.2 Add by magnet (`POST /api/v2/torrents/add`, urlencoded)

```http
POST /api/v2/torrents/add HTTP/1.1
Host: decypharr:8282
Authorization: Bearer <api_token>
Content-Type: application/x-www-form-urlencoded

urls=magnet:?xt=urn:btih:<info-hash>&dn=<name>&tr=<tracker>
&category=audiobooks
&sequentialDownload=true
```

- `urls` is newline-separated for multiple items (Decypharr `strings.SplitSeq(urls, "\n")`).
- `category` is **required** — it becomes the Arr name (`arr is required` otherwise).
- `sequentialDownload=true` is a Decypharr repurpose of qBittorrent's
  `sequentialDownload`: it **forces `action = download`** regardless of the global
  `default_download_action`.
- Optional `debrid=<provider-name>` selects the provider (else all/config default),
  `firstLastPiecePrio=true` strips tracker URLs (`rmTrackerUrls`).

Success → `200` with **empty body**. Failure → JSON:

```json
{ "error": "arr is required", "code": "provider_error", "retryable": true, "permanent": false }
```

with `502` for provider/arr errors, `400` for `invalid_magnet`/`invalid_torrent`,
`401` for auth.

### 4.3 Add by `.torrent` (multipart)

```http
POST /api/v2/torrents/add HTTP/1.1
Host: decypharr:8282
Authorization: Bearer <api_token>
Content-Type: multipart/form-data; boundary=----abr

------abr
Content-Disposition: form-data; name="category"

audiobooks
------abr
Content-Disposition: form-data; name="sequentialDownload"

true
------abr
Content-Disposition: form-data; name="torrents"; filename="release.torrent"
Content-Type: application/x-bittorrent

<binary .torrent bytes>
------abr--
```

`torrents` is the qBittorrent field name; Decypharr reads
`r.MultipartForm.File["torrents"]` and parses the file to an infohash →
magnet. Both `urls` and `torrents` may be sent together.

### 4.4 ABR source → payload mapping

| `TorrentSource` field | Send as |
|---|---|
| `magnet_url` (non-empty) | `urls=<magnet_url>` in an urlencoded body (preferred) |
| `download_url` (a `.torrent` URL) | ABR GETs it first (reuse the existing `_get_torrent_info_hash`/torf `Torrent.read_stream` handling and `NonHttpUrlRedirectClientError` magnet-redirect branch in `app/internal/prowlarr/prowlarr.py`), then multipart `torrents` |

The returned download id is the **info hash**, computed client-side (the add
response is empty): `_info_hash_from_magnet(magnet_url)` for magnets, or
`Torrent.read_stream(...).infohash` for `.torrent` — both already exist in
`app/internal/prowlarr/prowlarr.py`.

### 4.5 Native `/api/add` (simpler alternative worth knowing about)

Decypharr's first-party API is *cleaner* for an ABR-owned client and lets ABR set
the action explicitly instead of abusing `sequentialDownload`:

```http
POST /api/add HTTP/1.1
Host: decypharr:8282
Authorization: Bearer <api_token>
Content-Type: application/x-www-form-urlencoded

arr=audiobooks&action=download&downloadUncached=true&urls=magnet:...&debrid=<provider>
```

- Accepts `urls` (newline magnets), `files` (`.torrent`), `nzbURLs`/`nzbFiles`,
  `arr` (=category), `action` (`download`/`symlink`/`none`…), `downloadUncached`,
  `downloadFolder`, `debrid`.
- Returns a JSON **array** with per-item `status`/`error` (so immediate
  debrid-submit failures are visible), unlike the qBittorrent mock's empty 200.
- State via `GET /api/torrents?hash=<infohash>` (§7).

Using `/api/add` + `GET /api/torrents` + `GET /version` (Bearer) is the most
honest "first-class" ABR integration; the qBittorrent-compatible endpoints in
4.1–4.3 are exactly what Prowlarr uses and are required for Path B.

## 5. Config fields for a future `DecypharrClient`

Minimal set, and where each maps against the existing ABC/config pattern
(`app/internal/downloads/config.py` uses `StringConfigCache` key pairs):

| Config field | Required | Notes / default |
|---|---|---|
| `host` | yes | `decypharr` or IP; no path |
| `port` | yes | default `8282` |
| `use_ssl` | no | default false |
| `api_token` | yes (or user/pass) | Bearer token (Settings → Auth). Alternative: `username`/`password` for the cookie flow |
| `category` (Arr name) | **yes** | non-empty; becomes the Arr/category. Must match a Decypharr Arr for per-Arr credential auth; a bare throwaway name works for token auth |
| `debrid` (provider name) | optional | set to pin a provider (e.g. `AllDebrid`); empty = all/config default |
| `force_download` | recommended `true` | qbit path → send `sequentialDownload=true`; native path → `action=download` |
| `download_uncached` | recommended `true` | audiobook trackers are rarely cached; otherwise the hearsay gate may reject the watch |
| `download_dir` | Decypharr-side | used only for docs/expectations — ABR cannot set it per-request (`savepath` ignored); set in Decypharr and share with ABS |

`test_connection()` → `GET /api/v2/app/version` (expect `v4.3.2`) or native
`GET /version` (no auth). `enqueue()`/`status()` semantics as in §2/§7. Reuse
`DownloadClientError` (`app/internal/downloads/aria2.py`) for HTTP/auth/add
failures, parsing the Decypharr `{"error","code","retryable","permanent"}` body.

## 6. Known blockers / risks

1. **`arr is required` (502).** Every add parses a non-empty `category`/`arr`;
   empty → `addMagnet`/`addTorrent` → `AddNewTorrent` returns `arr is required` →
   `502 provider_error`. For Path B that means a blank Prowlarr "Category" breaks
   the grab exactly as T0.1 described.
2. **`download_action` controls materialization — and the qBittorrent path uses the
   *global* default, not the per-Arr value.** `handleTorrentsAdd` sets
   `action = cfg.DefaultDownloadAction` (default `symlink`) and only overrides when
   `sequentialDownload=true`. `symlink` needs a working FUSE/NFS mount; `none`
   leaves bytes only in the mount/store; **`download` writes files to local disk.**
   For ABS you want `download` (or per-Arr `download_action` via the native API,
   or force it per-request as in §4.2/§4.5).
3. **Debrid availability for audiobook trackers.** Decypharr = torrent → debrid
   only (`SendToDebrid`); `no debrid clients available` if none configured.
   Private audiobook tracker releases are frequently **not cached** on debrid;
   `download_uncached=true` is effectively required, and even then a provider may
   not be able to fetch a low-seed private tracker release. No first-party
   whitelist covers non-hoster sites — fine for magnet/`.torrent` content, but not
   a cure-all.
4. **Landing folder vs ABS watch folder.** `savepath` from ABR is ignored;
   completed files land in `<download_folder>/<category>` with Decypharr's release
   naming (no `out` rename). That folder must be a volume ABS watches, or mapped
   via path mapping / NFS / WebDAV; otherwise the post-download `abs_trigger_scan`
   finds nothing. Prowlarr's own docs warn that Prowlarr-grabbed releases "may
   require a manual import … from a non-standard directory."
5. **`downloaded` flag is set on acceptance, not completion.** Today
   `start_download`/`start_direct_download` set `book.downloaded = True` on 2xx.
   Decypharr `200` on add = "submitted to debrid", not "bytes on disk". Preserve
   that exact behavior for parity, or poll §7 before flagging.
6. **Auth identity confusion.** Decypharr login password ≠ Arr API key ≠
   Decypharr API token. `use_auth` on + wrong credentials → `401` on every
   `/torrents/*` call. A *saved* Arr is required only for the per-Arr
   credential style.
7. **No per-torrent id in the add response.** The qBittorrent mock returns empty
   `200`; ABR must compute the infohash itself to keep a `gid` for `status()`.
8. **`completion_on` is hardcoded to 0** in Decypharr's `/torrents/info`
   translation — do not use it; use `progress`/`status` (§7).
9. **Usenet is out of scope here.** NZBs go through Decypharr's SABnzbd mock
   (`/sabnzbd`), a different surface; keep `usenet` on its current path unless a
   separate task covers it.

## 7. Download-state surface for the `downloaded` flag

Two usable read surfaces:

**Native (`GET /api/torrents?hash=<infohash>`, Bearer).** Returns the `Entry`:

```json
{
  "info_hash": "…",
  "name": "…",
  "status": "downloading",      // "queued" | "downloading" | "downloaded" | "error"
  "progress": 0.72,             // 0..1
  "state": "downloading",       // qBittorrent-compat: "downloading" | "pausedDL" | "pausedUP" | "error" | "queuedDL"
  "category": "audiobooks",
  "save_path": "/data/audiobooks",
  "content_path": "/data/audiobooks/release",
  "last_error": null
}
```

**qBittorrent-compatible (`GET /api/v2/torrents/info?hashes=<infohash>`).** Returns
`hash`, `name`, `progress`, `state`, `amount_left`, `category`, `save_path`,
`content_path`, `magnet_uri`, `debrid`, `debrid_id`… (`completion_on` is always
`0`).

For marking `downloaded`:

- **Completion** = `status == "downloaded"` **and** `progress >= 1.0` (native).
  Do *not* use the qbit `state` field: a finished Decypharr entry keeps
  `state=downloading` mapping (`Entry.State` is a qbit shorthand, updated only on
  error/pause), and `completion_on` is stubbed to 0.
- **Failure** = `status == "error"` and/or `last_error` present.

`status(gid)` in a `DecypharrClient` should therefore call the native
`GET /api/torrents?hash=<gid>` (Bearer) and return that dict; the qbit
`/torrents/info` is the fallback if ABR must stay strictly qBittorrent-shaped
(but it can't distinguish `downloaded` vs still-`downloading` at progress 1.0
as cleanly).
