# T0.1 — Decypharr / external download-client investigation

Task: investigate the Decypharr integration question for the AudioBookRequestRu fork (FastAPI,
Russian audiobooks, direct HTTP audio sources such as knigavuhe.org).

**Status:** investigation spike (no application code changed).

**Bottom line / recommendation:** Decypharr is the wrong tool for direct HTTP audio. It is a
*torrent / magnet / NZB → debrid* gateway only; it cannot fetch a plain `http(s)://…/file.mp3`
URL from a scraped site that is not a debrid "file hoster". Keep Prowlarr (and Decypharr, if the
owner already uses a debrid provider for tracker-sourced releases) for `torrent`/`usenet` sources,
and add **aria2 (JSON-RPC)** as the download client for `direct` HTTP sources.

---

## 1. What Decypharr is, and how it integrates with Prowlarr

### 1.1 What it is

Decypharr (`sirrobot01/decypharr`, MIT, Go) is a **media gateway for debrid + usenet**. Its own
docs describe it as a "drop-in replacement for qBittorrent/Sabnzbd" that forwards torrents to debrid
providers (Real-Debrid, TorBox, AllDebrid, Debrid-Link, Premiumize) and/or streams NZBs directly
over NNTP, then exposes the resulting files via a FUSE/DFS or rclone mount, NFS/SMB, or WebDAV.

Source: https://github.com/sirrobot01/decypharr · https://docs.decypharr.com

### 1.2 How Prowlarr talks to it

Decypharr is registered in Prowlarr as an ordinary **qBittorrent download client** at
`http://<host>:8282` (Prowlarr → Settings → Download Clients → qBittorrent). This is exactly the
"Download Clients (Prowlarr Searches)" path in the Servarr wiki, which states:

> "If you intend to do searches directly within Prowlarr, you need to add Download Clients.
> Otherwise, you do not need to add them here. For searches from your Apps, the download clients
> configured there are used instead."

Source: https://wiki.servarr.com/prowlarr/settings#download-clients

Prowlarr's qBittorrent client driver speaks the standard qBittorrent Web UI API against the mock
endpoint Decypharr exposes (`pkg/server/qbit/routes.go`):

- `POST /api/v2/auth/login`
- `POST /api/v2/torrents/add` (magnet in the `urls` form field, or the `.torrent` file in the
  multipart `torrents` field, plus a `category` field)
- `GET /api/v2/torrents/info`, `/torrents/delete`, `/torrents/categories`, `/app/version`,
  `/app/webapiVersion`, `/app/preferences`, `/app/buildInfo`, etc.

Sources:
- https://raw.githubusercontent.com/sirrobot01/decypharr/main/pkg/server/qbit/routes.go
- https://docs.decypharr.com/reference/api (QBitTorrent API section)

On the Prowlarr side, a "grab" legs through the same code path as Prowlarr's own UI download
button: Prowlarr re-queries the indexer for that release's fresh tokenized URL, obtains the
`.torrent`/magnet, and submits it to the download client chosen for Prowlarr-searches. ABR's
`POST /api/v1/search {guid, indexerId}` is just that grab endpoint — it is not an ABR-specific
invention. (Confirmed by multiple third-party Prowlarr clients: `golift.io/starr/prowlarr.Grab`,
"`ProwlarrClient::grab(guid, indexerId)` POSTs the same endpoint Prowlarr's own UI uses".)

Sources:
- https://wiki.servarr.com/prowlarr/search
- https://pkg.go.dev/golift.io/starr/prowlarr

## 2. Is there a known incompatibility with ABR's `POST /api/v1/search {guid, indexerId}` flow?

There is **no first-party documented "Prowlarr → Decypharr grab is broken" bug**, and no matching
issue exists on `markbeep/AudioBookRequest` (0 results for "decypharr"). ElfHosted even documents
AudioBookRequest + Decypharr as a supported combo ("You'll need to configure Decypharr as a
downloader in Prowlarr itself").

Source: https://docs.elfhosted.com/app/audiobookrequest/

However, **Decypharr's qBittorrent mock is not a generic qBittorrent.** Reading its handlers shows
the grab only succeeds when a set of Decypharr-specific preconditions hold, none of which the plain
ABR/Prowlarr grab guarantees:

1. **A non-empty `category` that resolves to an "Arr".** `POST /api/v2/torrents/add` parses the
   `category` form field and resolves it to a registered Arr (`q.manager.Arr().Get(category)`). The
   `AddNewTorrent` guard is explicit:

   ```go
   if importReq.Arr.Name == "" {
       return fmt.Errorf("arr is required")
   }
   ```

   Prowlarr only sends a category if the qBittorrent download-client entry in Prowlarr has its
   **"Category"** field populated with a value that also exists in Decypharr as an Arr name. If it
   is left blank (the default) the add returns `arr is required` → Decypharr answers `502
   provider_error` → Prowlarr reports a failed grab → ABR's `start_download()` raises
   `DownloadFailed`. This is the most likely concrete failure behind the owner's report.

2. **Authentication.** `use_auth` (Decypharr's default pattern) verifies the qBittorrent
   username/password against Decypharr's user DB or API token, *or* against a saved Arr's host +
   API key. Prowlarr supplies generic qBittorrent credentials; if they don't match a Decypharr
   credential, every `/api/v2/torrents/*` call is rejected with 401.

3. **At least one configured debrid client.** `SendToDebrid` returns `no debrid clients available`
   if none is configured. The torrent is never "downloaded" locally — it is submitted to debrid.

4. **Post-download materialization.** Decypharr's completion model is oriented around media *Arrs*
   (Sonarr/Radarr/Lidarr) that have categories, root folders, and import handling. Prowlarr is
   fire-and-forget: it has no library/import, so even a successful debrid submit only lands in
   Decypharr's queue; making bytes appear on local disk depends on that category's
   `download_action` (`symlink` needs a working mount; `download` writes files locally; `strm`/`none`
   produce no media usable by Audiobookshelf).

Sources (evidence for items 1–4):
- https://raw.githubusercontent.com/sirrobot01/decypharr/main/pkg/server/qbit/http.go
- https://raw.githubusercontent.com/sirrobot01/decypharr/main/pkg/server/qbit/context.go
- https://raw.githubusercontent.com/sirrobot01/decypharr/main/pkg/manager/processor.go
- https://docs.decypharr.com/guides/arrs

**Conclusion for #2:** the incompatibility is not in ABR's HTTP call shape (it is the standard
Prowlarr grab), but in Decypharr's category/auth/debrid-routing requirements that Prowlarr-style
manual grabs don't naturally satisfy. If the owner still wants Decypharr for *tracker* sources, the
fix is purely configuration on the Prowlarr side (set the qBittorrent client's Category to a
Decypharr Arr name, supply Decypharr credentials, configure a debrid provider and a
`download`-action), **not** an ABR code change.

## 3. Is Decypharr the right tool for DIRECT HTTP audio files?

**No.**

- Decypharr's add surface accepts only **magnet URIs** or **`.torrent` files** (and NZBs via the
  SABnzbd mock). See `handleTorrentsAdd`: it reads `urls` (parsed as magnet) and the multipart
  `torrents` file field. There is no endpoint that takes an arbitrary `http(s)://…/file.mp3` URL and
  downloads it.
- The debrid providers behind Decypharr accept either torrent/magnet infohashes or a **whitelist of
  file-hosting sites** they support for "unrestricting". `knigavuhe.org` is a plain self-hosted
  audiobook site, not a debrid-supported hoster, so even a debrid "unrestrict link" call would not
  apply.

Sources:
- Decypharr `/add` handler: https://raw.githubusercontent.com/sirrobot01/decypharr/main/pkg/server/qbit/http.go
- Decypharr "What it does": https://docs.decypharr.com

So Decypharr cannot help with the knigavuhe direct-mp3 use case at all. The distinction to keep:

| Input | Protocol | Correct client |
|---|---|---|
| magnet / `.torrent` / NZB | torrent / usenet | Prowlarr → (debrid: Decypharr, or qBittorrent) |
| plain `http(s)://…/file.mp3` from a scraped page | **direct HTTP** | **aria2 (JSON-RPC)** |

## 4. Recommended download client for the direct-HTTP case

### 4.1 Evaluation

| Candidate | Verdict |
|---|---|
| **aria2 (JSON-RPC)** | ✅ **Recommended.** Purpose-built multi-protocol downloader (HTTP(S)/FTP/SFTP + torrent/metalink). Remote-control JSON-RPC (`aria2.addUri`), segmented + parallel connection downloads, retries, resume, per-download `dir`/`out`, custom `header`/`referer`/`cookie`/`user-agent` (needed to satisfy knigavuhe-style anti-bot checks), minimal footprint, well-known Docker images. Ideally matched to "external download client" in the plan (§6 of plan.md). |
| Decypharr | ❌ Only torrent/magnet/NZB→debrid. No direct-HTTP. |
| in-app `aiohttp` download | ⚠️ Works for one-shot fetches but no queue/resume/retry/rate-limit semantics; reinvents download management the plan explicitly wants external. |
| pyLoad | ⚠️ Overkill; oriented to one-click hosters/web UI. Consider only later if debrid-style hoster support is ever required. |
| qBittorrent | ❌ Torrent-only. |

### 4.2 aria2 configuration surface (fields the app must know)

aria2 RPC server is enabled by:

```
aria2c --enable-rpc --rpc-listen-all --rpc-listen-port=6800 --rpc-secret=<token> --dir=/downloads
```

App-config fields to model in `downloads/config.py` / Settings UI:

| Field | aria2 equivalent | Notes |
|---|---|---|
| `host` | RPC endpoint host (default `localhost`) | RPC is HTTP; endpoint path is `/jsonrpc` |
| `port` | `--rpc-listen-port` (default `6800`) | |
| `rpc_secret` | `--rpc-secret <TOKEN>` | sent as `token:<TOKEN>` first param; omit if disabled |
| `dir` | `--dir` / per-request `dir` option | base download directory (shared volume with app/Audiobookshelf) |
| `out` | per-request `out` option | final filename, relative to `dir` |

Recommended additional per-download options for knigavuhe-style sources: `header` (array, e.g.
`Referer: …`, `Cookie: …`), `user-agent`, `referer`, `split` / `max-connection-per-server`,
`continue=true`, `allow-overwrite=false`, `auto-file-renaming=true`.

### 4.3 Concrete JSON-RPC calls

Endpoint: `POST http://<host>:6800/jsonrpc` (Content-Type `application/json`).

1. **Capability probe / test-connection** (no secret required):

   ```json
   {"jsonrpc":"2.0","id":"abr-1","method":"system.listMethods","params":[]}
   ```

   (`system.listNotifications` works the same way. `aria2.getVersion` can be used instead when a
   secret is configured, to also validate the token.)

2. **Add a direct HTTP download** (`aria2.addUri`, single source):

   ```json
   {"jsonrpc":"2.0","id":"abr-2","method":"aria2.addUri",
    "params":[
      "token:SECRET",
      ["https://knigavuhe.org/…/book.mp3"],
      {"dir":"/downloads/audiobooks","out":"author-title.mp3","header":["Referer: https://knigavuhe.org/"]}
    ]}
   ```

   Response: `{"id":"abr-2","jsonrpc":"2.0","result":"<gid>"}` — the GID is stored for status
   polling via `aria2.tellStatus`.

   Multi-mirror form (same resource, order = fallback): `["https://host/a.mp3","https://mirror/b.mp3"]`.

3. **Poll status** (optional, for UI/notification state):

   ```json
   {"jsonrpc":"2.0","id":"abr-3","method":"aria2.tellStatus","params":["token:SECRET","<gid>"]}
   ```

   Relevant keys in the result: `status` (`active`/`waiting`/`paused`/`complete`/`error`/`removed`),
   `totalLength`, `completedLength`, `downloadSpeed`, `files`, `errorMessage`.

Sources:
- https://aria2.github.io/manual/en/html/aria2c.html#rpc-interface
- https://aria2.github.io/manual/en/html/aria2c.html#aria2.addUri (method signature, `dir`/`out`, secret token)
- https://aria2.github.io/manual/en/html/aria2c.html#rpc-authorization-secret-token

## 5. Recommended integration design for this app

1. **`DownloadClient` abstraction.** Introduce an ABC (`app/internal/downloads/client.py`) with a
   narrow interface, e.g. `test()`, `add_uri(urls, dir, out, **opts) -> download_id`, and
   `status(download_id)`. Implement `Aria2Client` (JSON-RPC over the existing `aiohttp`
   `ClientSession`) and optionally a `ProwlarrClient` wrapper around `start_download()` so normal
   grabs look the same through one dispatch point.

2. **Route by source protocol, not by backend flag.** In `query.py` / `download_backend.py`:

   - `TorrentSource` / `UsenetSource` (protocol `torrent`/`usenet`) → **Prowlarr**
     (`POST /api/v1/search {guid, indexerId}`), exactly as today. Prowlarr's own download client
     (qBittorrent **or** Decypharr) handles those; no ABR change needed for Decypharr, only
     Prowlarr-side category/auth config (see §2).
   - `DirectSource` (protocol `direct`, e.g. knigavuhe mp3 URLs) → **aria2**
     (`aria2.addUri` with `dir` = target book folder, `out` = sanitized filename, plus `referer`/
     `header`/cookies the scraper discovered).

3. **Config.** `downloads/config.py` stores `host`, `port`, `rpc_secret`, `base_dir` (override per
   request via `dir`) and, for knigavuhe-type sources, optional target-parent naming. Reuse the
   `StringConfigCache` pattern + a Settings page like the Prowlarr one. Add an aria2 service (and a
   `test` compose profile) in `docker-compose.yml` with a shared download volume.

4. **Notification/state.** Mirror the existing `EventEnum.on_successful_download` /
   `on_failed_download` emission, but for direct sources the "success" signal is
   `aria2.tellStatus(...) == "complete"` (or the GID being accepted as queued, per phase-3
   acceptance criteria), rather than Prowlarr's HTTP 2xx.

5. **Keep Decypharr orthogonal.** Only used (optionally) as Prowlarr's download client for debrid
   torrents; it is never a target for `direct` sources.
