# T0.2 — livelib.ru scraping spike

**Verdict:** livelib.ru **can** be scraped to provide Russian audiobook metadata. The search
page exposes a stable, per-edition `data-book_id` attribute that carries the canonical WORK id,
and each edition/book page embeds a complete `schema.org/Book` JSON-LD blob (title, author,
cover, genres, full annotation, publication year, ISBN, publisher, rating) plus a
`ItemList` of similar books.

**One important correction to the task assumptions:** `https://www.livelib.ru/work/<work_id>`
returns **HTTP 404** for the legacy 6-digit work ids found in search results (e.g. 664551).
livelib is mid-migration to a Next.js frontend; `/work/` now expects the *new* 10-digit work ids
(e.g. `/work/1000269075-master-i-margarita-mihail-bulgakov` → 200). The legacy work id still works
with `/book/<work_id>/editions` (the work's edition list). Full metadata lives on the edition page
(`/book/<edition_id>-<slug>`), which is exactly where a search-result card links via `data-link`.

**Second important finding (networking):** livelib's DDoS-Guard returns `403` for plain
HTTP/1.1 clients on the Next.js pages (book/work/editions); those pages require **HTTP/2**.
The legacy PHP search page (`/find/…`) still accepts HTTP/1.1. Verified:

| client | `/find/…` (PHP) | `/book/…-slug` (Next.js) |
|---|---|---|
| `curl --http1.1` | 200 | **403** |
| `curl --http2` | 200 | **200** |
| Python `urllib`/`requests` (HTTP/1.1) | 200 | **403** |

Practical consequence for the app: `requests`/`aiohttp` (HTTP/1.1) cannot fetch the detail pages;
use an HTTP/2 client (`httpx[http2]`, or shell out to `curl --http2`). The spike script falls back
to `curl --http2` automatically.

## 1. Search page — `https://www.livelib.ru/find/books/<query>`

* Server: PHP (legacy). Content-Type `text/html; charset=UTF-8`.
* Cyrillic query must be URL-encoded (e.g. `Мастер%20и%20Маргарита`). The page's own
  `link rel=next` uses `%20` encoding.
* Pagination: `/find/books/<query>/~2`, `~3`, … ; sort via `/…/<query>/relevance`.
* Default list view class: `#objects-block` → `.object-wrapper-outer` → `.object-wrapper.object-edition.ll-redirect`.

Result card structure (raw markup, compacted):

### Concrete selectors

| Field | Selector / pattern |
|---|---|
| Result card | `#objects-block .object-wrapper.object-edition` |
| Edition URL | card `@data-link` (e.g. `/book/1018128325-master-i-margarita-mihail-bulgakov`) |
| Title | `.brow-title a.title` (text) |
| Author | `a.description[href^="/author/"]` (text); author id+slog in the same `href` |
| Cover | `span.object-cover` inline `style` → regex `background:url\(([^)]+)\)` |
| Genres | `.brow-genres a.label-genre` (plural; text of each) |
| **Work id** | `[data-book_id]` → `@data-book_id` (the span `.challenges-book-load` inside the card) |
| Edition id | `[data-edition_id]` (on `.userbook-container` / `.ub-container`) |

### `data-book_id` = canonical WORK id — CONFIRMED

Every one of the 20 cards on the "Мастер и Маргарита" page carries exactly one
`data-book_id`, and its value is the canonical work id:

* present on **20/20** cards (`re.findall(r'data-book_id="(\d+)"')` returns 20 matches),
* identical, per card, to the `ub-book-<id>` class and to `/book/<id>/editions` link id.

Top results for "Мастер и Маргарита":

| title | `data-book_id` (work) | work editions link |
|---|---|---|
| Мастер и Маргарита | **664551** | `/book/664551/editions` (445 изд.) |
| Белая гвардия. Мастер и Маргарита (сборник) | 104148 | `/book/104148/editions` |
| Мастер и Маргарита (сборник) | 6104122 | `/book/6104122/editions` |
| Мастер и Маргарита (сборник) | 2404795 | `/book/2404795/editions` |
| Мастер и Маргарита (сборник) | 7243849 | `/book/7243849/editions` |

Caution: the same work may appear under several `data-book_id`s (e.g. the plain novel is 664551,
while combined "сборник" editions are different work ids 6104122, 2404795, …). For deduping
audio editions of the *same work*, prefer matching on the work id + normalized title rather than
title alone.

## 2. Work / detail pages

`/work/<legacy_id>` → **404** (Next.js). Three working page types provide metadata:

### 2a. Edition/book page — `/book/<edition_id>-<slug>` (canonical, richest)

This is the page a search card's `data-link` points to (e.g.
`/book/1018128325-master-i-margarita-mihail-bulgakov`). It behaves as the canonical "book" page:
title, author, cover, genres, full annotation, ISBN, publication year, publisher, rating, an
`EditionsBlock` linking to `/book/<work_id>/editions` ("445 изданий"), and a "Похожие книги"
(similar) widget.

Crucially it embeds a `schema.org` JSON-LD `<script id="orbitalis-book-card-schema" type="application/ld+json">`
with an `@graph` containing the fields below. This is machine-readable and is the most robust
parse target — no fragile CSS selectors needed for these fields.

**`@graph[].@type == "Book"` fields observed** (Мастер и Маргарита, edition 1018128325):

| JSON-LD key | value |
|---|---|
| `name` | Мастер и Маргарита |
| `url` | `https://www.livelib.ru/book/1018128325-master-i-margarita-mihail-bulgakov` |
| `image.url` | `https://s1.livelib.ru/boocover/1018128325/200x305/86ee/Mihail_Bulgakov__Master_i_Margarita.jpg` |
| `isbn` | `978-5-0063-0439-0` |
| `genre[]` | `["Мистика", "Литература 20 века", "Русская классика"]` |
| `datePublished` | `2026-01-01T00:00:00+03:00` (→ year 2026) |
| `author.name` / `author.url` | Михаил Булгаков / `/author/408-mihail-bulgakov` |
| `publisher.name` / `publisher.url` | Альпина Паблишер / `/publisher/1272-alpina-pablisher` |
| `aggregateRating` | `ratingValue: 9.1` (10-point scale), `ratingCount: 111314` |
| `description` | full annotation (~2 KB) |
| `additionalProperty[]` | reviews count, quotes count, "В топ-100" flag |
| `interactionStatistic[]`, `review[]`, … | engagement stats / sample reviews |

Other `@graph` nodes: `BreadcrumbList`, `ItemList` (similar books), `CreativeWork` (quotes), `WebSite`.

**Selector fallbacks when JSON-LD is absent:** page `<h1>` = title; `a[href^="/author/"]` = author;
genre chips link to `/genre/<name>`; cover image `img[src*="/boocover/"]`.

### 2b. Work editions list — `/book/<work_id>/editions` (reachable from the legacy work id)

* Title: `Произведение «Мастер и Маргарита» – Михаил Булгаков – Все издания`.
* Lists editions (20 on page 1 of 445) as `href="/book/<edition_id>-<slug>"`.
  Extract with `href="/book/(\d+)-([a-z0-9-]+)"`.
* Has a breadcrumb back to the canonical edition page. No JSON-LD here, no description/genres —
  it is **not** a rich metadata source, only an edition list. This is the captured fixture
  `work-664551.html`.

### 2c. New-style work page — `/work/<10-digit-id>-<slug>` (Next.js)

For "works" that exist as standalone Proizvedenie entities (e.g. Bulgakov's short story
`/work/1002135609-chelovek-s-gradusnikom-mihail-bulgakov`), this route returns a page with the
same JSON-LD `Book` node (title/genres/description/rating) and a similar-books `ItemList`.
The new-style work ids are 10 digits; they are **not** the 6-digit `data-book_id` from search.
Use `/find/works/<query>` to discover them. There is no obvious id↔id mapping link on the pages
we inspected, so for the app we recommend treating `data-book_id` + the edition `data-link` as the
canonical pair rather than chasing the new `/work/` ids.

## 3. JSON / unofficial API endpoints

* **Autocomplete (unofficial JSON endpoint):** `POST /main/search`
  * Body (form-encoded): `text=<query>`, `object_alias=booksauthors`, plus
    `result_element`, `width`, `start`, `limit`, `is_new_design`.
    (Discovered in the legacy base JS bundle; the header search box carries
    `data-object_alias="booksauthors"` and the form posts to `/find`.)
  * Returns `Content-Type: application/json`: `{"error_code": 0, "content": "<HTML snippet>"}`.
    The `content` field is an **HTML** dropdown (not clean book records), so it still needs HTML
    parsing/regex. Useful as a quick typeahead only.
  * `Start`/`limit` paginate; `object_alias` selects entity (books+authors, etc.).
* **Embedded JSON-LD (best structured source):** `<script type="application/ld+json">` on the
  edition/book and work pages (see §2a). Parse with `json.loads` after a single regex — no HTML
  parser required.
* No public/undocumented JSON REST API for full book records was found; the Next.js pages embed
  a React Server Component (`self.__next_f.push`) payload that also contains the data, but the
  JSON-LD block is much cleaner and sufficient.

**Conclusion:** HTML parsing is required for search results (the autocomplete is JSON-wrapped-HTML),
but the *detail* metadata can be read from the JSON-LD block without an HTML parser.

## 4. Similar books / recommendations

Available, no keyword-search fallback needed:

* **On edition & work pages:** a `<section class="SimilarArts_SimilarArts__…">` with
  `<h2 id="similar-arts">Похожие книги</h2>` and `BookCard` cards linking to `/book/…` or `/work/…`.
* **Dedicated page:** `/book/<edition_id>/similar` (links from the "Все" button).
* **As structured data:** the JSON-LD `ItemList` node on the same page mirrors it
  (20 items = similar/related books with `name` + `url`). The spike parses this directly.
* The `ItemList` is mostly *other editions/works by the same author* rather than true
  collaborative-filtering recommendations, but it is populated and stable.
* Fallbacks if more recommendations are needed: genre pages `/genre/<name>`
  (also seen: `/genre/getbooklist`, `/book/similar` XHR endpoints in the legacy JS bundle).

## 5. Python HTML parsing dependency — recommendation

**Recommend `selectolax`** for the production parser:

* CSS-selector API maps 1:1 to the selectors above; fast (C-based, Lexbor/Modest engine);
  provides wheels for macOS/Linux x86_64/arm64; tolerant of the slightly messy PHP search HTML.
* Prefer it over `bs4` (slow, pure-Python dispatch; need extra `lxml` for speed) and over bare
  `lxml` (XPath is more verbose for this nested CSS-heavy markup).

**Can we avoid a dependency? Partly, and the spike does:**

* The **detail metadata** is fully extractable with stdlib `re` + `json` from the JSON-LD block
  (verified in the spike).
* The **search cards** are regular enough that stdlib `re` works (the spike parses all 20 cards
  correctly without a parser).
* So a zero-dependency PoC is feasible. But for maintainability against markup drift and for the
  autocomplete HTML, add `selectolax`. If minimizing native deps is a goal, `bs4` with the built-in
  `html.parser` is the safest fallback (pure Python), at the cost of speed.

## How to run the spike

```
python spikes/T0.2-livelib-scrape.py                       # live end-to-end (search → detail → editions → autocomplete)
python spikes/T0.2-livelib-scrape.py --use-fixtures tests/fixtures/livelib   # offline search + editions
```

Only stdlib is required; `curl` (with `--http2`) is used as the HTTP/2 fallback for the Next.js
pages. Politeness: single requests, 1.5 s delay between them, descriptive User-Agent.
